# ScalaAFA 恢复取证与分阶段方案（2026-09-20）

## 结论先行

当前不能继续启动 DataNode、不能恢复旧 dPP 验收文件、不能运行正式 CaaS 对比。原因不是单一的 Runner 没启动，而是数据路径和验收证据不一致：
- DataNode 已停止，避免继续把宿主根盘目录误当作 ScalaAFA 数据盘。
- DataNode 之前的实际挂载证据是 /dev/sda2 ext4 /，不是 NVMe/ScalaAFA 文件系统。
- HDFS fsck 看到 1,175 个块缺失，说明当前 NameNode 看不到原数据；不能据此断言原 ScalaAFA 盘永久丢失。
- 8092 guest 的 SPDK afa0 进程仍在，但 NVMf subsystem 只有 Discovery，没有导出在线数据 namespace。
- 8092 日志曾出现大量 AFA parity mismatch，且 repair=0；这要求先取证，不能盲目运行恢复或 scrub。
- dpp-online-validation.json 当前有效路径下不存在。两份历史报告已改名为 revoked 文件，即使内容 passed=true 也不能恢复为门禁文件。
- 最近 /api/dpp/run 只生成 scalaafa-dpp-*.json，源码标注 in-memory functional model 和 performance_claim=false；它不是在线 dPP 验证。

- Host-Local PV caas-hdfs-data-hostlocal → /data/xhf/caas-lsm/k8s-state/datanode-hostlocal。
- afa0-mode2.wal、meta*、devices*、afa-wal-source.tgz、femu-patched-source.tgz、recover-persistent-scalaafa.sh、dpp-online-verify.sha256 均存在待校验资产。
- revoked 报告：dpp-online-validation.revoked-20260918-0926.json 和 dpp-online-validation.revoked-20260918-1825.json。
- /data/xhf/caas-lsm/scalaafa-integration/dpp-online/dpp-online-validation.json 是源码集成目录副本，不是 Runner /results 当前有效门禁。

## 关键证据

DataNode 容器 mountinfo 和 df 显示：
```text
... /data/xhf/caas-lsm/scalaafa-pv /state/datanode ... - ext4 /dev/sda2 rw
```

只读 HDFS fsck 显示 CORRUPT、MISSING BLOCKS=1175、MISSING SIZE=2105007715 B。当前不能据此断言原卷不可恢复。
8092 guest 的 afa0 bdev 存活，但 nvmf_get_subsystems 只有 Discovery，未导出在线数据 namespace。/tmp/afa-recovered-vm.log 中存在历史 AFA parity mismatch。

## 恢复原则

1. 先复制和校验 WAL、元数据、FEMU 镜像和撤销报告，再进行连接或挂载。
2. 不覆盖原件；恢复和编译只能在副本或快照上进行。
3. 保持 DataNode=0、Runner 不提交任务、HDFS 不产生新写入。
4. 分层验证：FEMU → guest AFA → SPDK/NVMf → 宿主设备 serial → 文件系统只读检查 → HDFS 只读检查。
5. PVC Bound、PV label 和 CAAS_STORAGE_BACKEND 字符串不能替代真实设备证据。
6. dPP 门禁只能由当前链路重新生成，不能复制或改名历史 JSON。

## 分阶段方案

### 阶段 0：冻结（已完成）

保持 DataNode=0；不运行 recover-persistent-scalaafa.sh；不重启/停止 8092 SPDK/FEMU；不执行 e2fsck、mount、nvme connect、bench.sh 或 fio；不恢复 dpp-online-validation.json。

### 阶段 1：只读资产清单与校验

服务器负责人保存以下输出，不覆盖源文件：
```bash
sha256sum /data/xhf/scalaafa-persist/afa0-mode2.wal /data/xhf/scalaafa-persist/afa-wal-source.tgz /data/xhf/scalaafa-persist/femu-patched-source.tgz /data/xhf/scalaafa-persist/dpp-online-verify.sha256
find /data/xhf/scalaafa-persist/devices-mode2-clean1 -type f -exec sha256sum {} ;
find /data/xhf/scalaafa-persist/meta-mode2-clean1 -type f -exec sha256sum {} ;
stat /data/xhf/caas-lsm/k8s-results/dpp-online-validation.revoked-*.json
```

### 阶段 2：查明撤销原因

建立报告版本、生成时间、backend、通过内容、撤销时间/原因、是否可作当前门禁的对应表。必须回答撤销是否因 target 重启、DataNode 路径错误、parity mismatch、HDFS 数据变化或实验版本切换。

### 阶段 3：隔离恢复演练

在新 FEMU 设备组或副本上拆分运行恢复步骤；确认 guest SSH、元数据盘、WAL replay、afa0 UUID/容量、NVMf listener、serial/NQN 和只读 e2fsck。不得直接使用承载历史数据的当前在线设备。

### 阶段 4：重建真实 PV 路径

只有阶段 3 通过后，才让 scalaafa-pv 真正成为预期 NVMe/ext4 挂载，而不是根盘目录；记录 findmnt、serial、e2label、UUID；用临时只读 Pod 验证 mountinfo。

### 阶段 5：重新生成在线 dPP 验收

确认脚本确实操作 8092 online AFA，而不是内存模型。生成新的 /results/dpp-online-validation.json，包含当前 backend/NQN/serial、scrub、partial writes、故障恢复、HDFS fsck、生成时间、代码版本和 WAL hash。不能声称任意在途掉电原子性。

### 阶段 6：低风险系统 smoke

完整健康门通过后，才做一次最小 CaaS smoke；记录 backend、PVC、runner 镜像和配置 hash。

### 阶段 7：Vue 实时联调

本地只读适配层已经能接收 30082 WebSocket；真实样本需要服务器看板广播 sample/stream_point。真实执行接口仍需单独授权。

## 禁止快捷操作

- 不要复制 revoked JSON 为 /results/dpp-online-validation.json。
- 不要把 /api/dpp/run 的 in-memory 输出当作在线验证。
- 不要把 Host-Local 或根盘结果标成 ScalaAFA。
- 不要对 /dev/sda2 目录执行恢复脚本或裸 fio。
- 不要在不知道 NVMf 数据 subsystem 是否导出的情况下启动 DataNode。
- 不要删除 STORAGE_UNSAFE 标记来解锁。

## 当前建议

停在阶段 1/2 取证，所有恢复和在线验证操作分开审批。
